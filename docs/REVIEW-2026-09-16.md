# TARI 产品、设计与实现评审 — 2026-09-16

评审基线：`33bbec5` 加接手时已有的 Story schema、提交冲突和 reliability 测试改动。本文区分已复现缺陷、代码观察和产品建议；没有将建议当作现有产品能力。本轮未修改业务实现、调用真实 LLM、提交或推送。

> 后续进展：用户已授权转向低频参与、故事创作为主。本文保留评审时点的发现；之后实现的 Story 版本冲突保护、runtime transition 和写手上下文见 [产品方向](product-direction.md#当前交付与边界)，当前推进顺序见 [新版路线图](technical-roadmap.md)。

## 1. 总体判断

项目值得保留的核心是：以确定性运行时管理世界状态、选择后果和历史，并限制模型的权限。Campaign/Story 分离、SQLite 原子提交、可恢复编译与 Fake 测试也提供了可继续演进的基础。

主要不足是产品目标、模型输入和运行时保证还没有闭合：资料能编译，回合能返回，但这还不能证明玩家的行动产生了持续、可感知且一致的后果。当前应该优先验证这个闭环，而不是把多 Agent 数量、实体数量、全书编译完成或测试通过当作最终效果。

建议对外核心承诺聚焦为“玩家能够在一个记得选择及其后果的世界中持续扮演”。具体偏向原著探索还是自由改写、规则化 TRPG，仍以用户偏好为准。两个领域上下文继续独立，但短期选择一条主要体验作为产品验收对象。

## 2. 已复现的实现缺陷

所有复现使用临时 SQLite、Fake Agent 或本地捕获写手输入；没有网络调用。

### R1 / P0：旧快照可以覆盖已提交进展

涉及 `narrative/storage.py:359`、`storage.py:149` 和两侧 runtime。

分别在 Story 和 Campaign 中，从同一个第 0 回合 state 发起两个不同 request-id 的成功请求，两个请求都被接受。结果均为：完成事件有 2 条，快照仍为第 1 回合。Story 示例中的 `trust` 最终为 1。

这证明单次事务的原子性并未提供基于旧状态的提交冲突保护。HTTP 在等待模型期间，多个请求有机会读到同一快照；本次用顺序传入同一旧对象复现了其存储前提，尚未做 HTTP 并发压力测试。

修改方向：提交时在同一数据库事务内校验 expected version/turn，拒绝旧状态；按 campaign 或 session/branch 标识一次权威回合；错误应明确映射为冲突。请求占用/排队可减少重复生成，但不能只依赖进程内锁，也不应在等待 LLM 时长期持有 SQLite 写事务。

验收：同一旧版本的两个不同请求最多一个提交；另一请求明确冲突；历史、快照、结果表一致；覆盖独立 runtime/store 实例。

### R2 / P0：Campaign request-id 跨会话串用

涉及 `runtime.py:55`、`storage.py:88`。上一轮接手核验已复现：第二个 campaign 复用首个 campaign 的 request-id，会得到自己的快照和对方的回合结果。

修改方向：查询缓存时校验归属；短期沿用全局 key 但拒绝跨 campaign 复用。对同 key 不同 payload 的处理要明确：现有 Story 是重放首次结果，可保留兼容；若改为 payload 冲突错误，应作为明确的协议变更。

### R3 / P1：Story 选择效果可重复，也可被遗漏

涉及 `narrative/runtime.py:286` 和 author/provider 的效果构造。

`trust` 选择声明 `trust +1`。将 Fake author 的对应 patch 复制一次，runtime 接受并提交 `trust=2`；删除该 patch，也接受并提交 `trust=0`。原因是校验只检查每个 patch 是否属于允许集合，没有检查完整性与重复次数。

当前内置 provider 会生成预期 patch，因此不是宣称正常 provider 每次都会触发。但 runtime 的权限边界不应依赖某个 adapter 恰好正确。

修改方向：由 runtime 从选择计算完整 transition（目标、effects、reveal、choices、terminal、source refs）；写手只返回正文和可选诊断。移除 Fake/真实 author 里重复的权威数据拼装，让 adapter 无法删改或重复效果。保留兼容层时做精确的多重集校验。

### R4 / P1：来源引用没有形成完整校验边界

涉及 `story/bundle.py:147`、`narrative/runtime.py:241`、`story/decomposer.py:1692`。

将 fact 的 source_refs 指向不存在的 evidence，StoryBundle 验证仍通过；让 author proposal 返回不存在的引用，回合仍可提交。编译器的关系结构没有独立 source_refs 字段；实体引用放在任意 attributes 中，缺少同等严格的类型约束。

修改方向：定义 source/external/generated 等引用种类，明确手工故事包的合法引用规则；对于编译包，验证 evidence ID、源摘要、位置和所有引用。模型推断及系统生成结尾必须显式标记，不能伪装成原文引文。

证据粒度也需要提高：当前编译器将 fact 关联到章节，evidence 摘录为章首 600 字。这能指向来源章节，但不能单独证明章中任意事实受原文支持。应补充可定位的原文片段，并区分原文陈述、角色信念、编译推断及当前游玩时间线的事实。

## 3. 已验证的体验与协议缺口

### R5 / P1：Story 写手缺少游玩上下文

`narrative/providers.py:94` 的提示词包含标题、当前/目标 beat、目标文本、当前输入和最近事件类型；没有使用传入的 state，也没有传入历史叙事正文。

本次离线捕获 provider 消息：将玩家从 Ari 换成 Bea、增加敌对人设、把 trust 变成 -10，并将此前故事从“守卫帮助你”改成“守卫背叛你”，在当前输入和 beat 不变时，provider messages 完全相同。

因此玩家身份、关系变化、已知事实与对话连续性无法通过这些输入影响写手。改进优先于增加向量数据库：先建立受权限过滤的写手视图，包含玩家身份、当前场景、已提交后果、当前可知事实、近期公开对话和风格约束。不能简单把所有 state/Bundle 全量塞入 prompt。

验收：身份、公开历史与已提交关系变化会改变输入；私有事实不会混入公开写手视图；分支只读到自己可见的历史。

### R6 / P1：编译资料与可玩剧本之间缺少一步

`story/decomposer.py:1829` 为每个 arc 构造一个 beat，通常只提供一个通往下一 arc 的 continue 选项。手工故事包可以拥有分支，但自动编译路径并未生成有实际后果的决策空间。

这适合“沿原著分段探索”的早期产品，不足以支撑自由扮演的承诺。小说中的全知摘要还可能提前包含结局信息，不能直接当作玩家此刻的视角。

建议区分三类产物：来源知识、可玩场景、当前会话状态。可玩场景需要当前时点、角色目标、冲突、可用信息、可执行行动及后果条件。先做一段 15–30 分钟的短篇场景，覆盖至少两条行为结果不同的路径；无需首先预生成整本书的分支树。

自由输入目前不能改变 beat，这是明确的 MVP 取舍。若目标是自由扮演，可加“意图解析→runtime 判断条件与后果→写手表达”的有限行动协议；无法识别的行动应明确澄清或拒绝，避免正文说成功而状态毫无变化。

### R7 / P1：Campaign plan 与 resolution 没有完整衔接

`agents.py:277` 的 gm_resolve 接受 view、input 和 roll，没有接收前一步 plan；prompt 也没有携带 plan 中的检定说明及 stakes。两阶段复用 GMDecision，runtime 将 plan 用于掷骰和 debug，但没有检查 resolution 是否履行先前约定。

建议拆分 GMPlan/GMResolution，并把已验证 plan 与 roll 显式传入裁定。可机械检查的结果用 typed 字段表达；自然语言后果的语义一致性仍需要单独评估，不能声称 Pydantic 或路径白名单可以完全证明。

### R8 / P2：公开概念超过了实际行为

Story 的 strict/guided/sandbox 当前被保存但没有对应 runtime 分支；memory_policy 等身份字段未形成行为。StorySessionState 只绑定 story_id，没有绑定 Bundle 内容版本；Web 每次重新按 story_id 查找资源，缺少旧会话持续使用原素材版本的保证。

建议只暴露已实现的策略，或明确标注预留。将会话绑定到 bundle digest/版本，对素材变化明确拒绝或显式迁移。不要把“字段存在”等同于“能力存在”。

## 4. 架构和工程上的调整

保留两侧独立 domain/runtime，保留小型共享 persistence/transport。首先完善权限、事务和上下文合同，再拆大文件；单纯把 2235 行 decomposer 拆成几个文件不会自动补上这些缺口。

建议按实际职责拆分编译器：阶段调度与缓存、提取、来源验证、场景构造、导出。各阶段通过已验证的 artifact 连接，避免新的通用工作流框架过早侵入领域。Web 拆分后仍应是输入/错误/输出适配器。

多 Agent 的收益需要测量。当前 Campaign 的 Actor 路径依次调用 plan、resolve、actor、audit、wrap；更长的调用链可能增加等待、成本和失败机会，但本轮没有真实模型延迟数据，不能给出数值结论。先记录每阶段耗时、调用量、失败和玩家可感知质量，再用同场景比较简化流程；保留确实带来质量或隔离收益的角色。

已有测试和恢复机制有价值，但本次缺陷表明门禁还没覆盖关键反例。建议增加：旧版本竞争、重复/遗漏 effects、引用伪造、素材版本变化，以及身份/知识投影的对照测试。100 回合只是样本规模，必须交代故障分布、恢复行为及不变量。CI 应尽早运行离线门禁；真实 LLM 评估独立、显式触发。

旧设计提案与现行文档中关于 CoT 展示、提交时点等内容存在不同口径，应标记旧提案被何种决策替代。玩家进度可用明确阶段事件，调试信息与公开内容保持独立。

公开部署前的鉴权、ownership、限流和隐私投影仍然必要；本地原型阶段不必为此先建设复杂多租户平台。

## 5. 对上一份执行计划的修订

1. **正确性批次**：R1 旧状态冲突、R2 request-id 归属、R3 runtime 自行执行 transition、R4 引用边界。同步补针对性回归和 CI，保留旧接口的可解释兼容行为。
2. **连续性批次**：写手视图、Bundle 版本绑定、明确真正可用的策略；用短篇测试身份、知识、关系与分支连续性。
3. **产品验证批次**：按用户确定的主体验制作一个 15–30 分钟样本；衡量选择后果、状态与正文一致性、重载连续性、完成率及回合等待。提供最小客户端即可，无需先完成整套前端改造。
4. **可靠性与扩展批次**：将上述反例纳入两侧故障报告；完成 Campaign plan/resolution 合同和重试预算。Story 的主要体验不必等待所有 Campaign 扩展完毕，公开发布仍需相应 gate。

优先级取决于主体验选择，但 R1–R4 不依赖该选择。暂不扩展多 Actor、全书自动分支树、向量记忆或公共客户端协议。

验证范围：代码审查与离线最小复现；不包含真实 LLM 文风/语义评测、浏览器实玩、HTTP 并发压测或生产部署审计。上轮已有全量测试通过，本轮没有修改实现，也未重复运行相同全量门禁。
