# 连续阅读试读记录 — 2026-09-17

## 第一轮：工程闭环通过，叙事质量不通过

使用用户明确授权的现有外部 LLM 服务，发送 TARI 原创《最后一班渡船》及测试上下文。按授权上限生成 8 个场景：公共开头 2 个、留下分支 3 个、渡河分支 3 个。端点与凭据不写入文档。

- 全程约 117.66 秒。
- 两条路线均到达结束状态，存档分别记录 `letter_delivered=false/true`。
- 每条路线各有一次关键决定，公共开头在 runtime 层停于选择点。
- 留下路线连同公共开头共 6402 字符；渡河路线连同公共开头共 7222 字符。两项包含相同的公共开头，不能相加当作独立输出总量。
- 本地报告 `runtime-data/reading-evaluation/report.json` 的 `status=complete` 仅表示请求全部执行完成，不表示文学质量合格。

人工阅读发现：

1. 第一场“第一次铃响”就替玩家打开储物间、登船并离岸，提前解决了本应等待玩家的分歧。
2. 第二场“一分钟”已写到对岸收信人开门，但存档才到选择点；正文与权威状态明显不同步。
3. 留下分支随后把人物放回出发岸；渡河分支提前送达后又回到渡口，再叙述渡河后的阶段，空间与时间连续性混乱。
4. 后续反复使用摸信封、雨势渐小、夜晚不冷等表达，部分段落近似复制。
5. 原始素材中收信人明早离城的期限被老师“不急、明天送也行”的台词弱化，损害玩家选择的真实代价。

结论：该轮正文不作为合格示范；它证明只检查 SQLite 状态和传入历史仍然不够。测试不能把 runtime 的 `awaiting_choice` 等同于正文真的停在选择之前。

## 针对性修改

- 每个样本场景增加 `boundary`：起始事实、必须到达的结束事实、禁止提前发生的事件。
- 写手上下文显式携带是否等待玩家决定，以及尚未选择的方向。提示词要求只写当前目标场景、在边界停止、保留既有期限和选择代价。
- 带 boundary 的场景在生成后增加一次独立审查调用，检查越界、擅自决定、连续性和大段复述。拒绝或无效审查结果会在发布前终止；之前的场景不受影响。
- 不自动无限修订；用户可用同一请求 ID 重试。每个带 boundary 的场景尝试最多执行写作和审查两个应用层调用，底层 transport 自身的重试另计。
- Fake 写手仍用于离线流程验证，不声称具备语义审查能力。旧资源没有 boundary 时仍走单次写作，保持兼容。

审查仍由模型完成，可能误判或漏判，不是文学正确性的形式化证明。离线测试只证明审查失败不会发布、结构化边界正确传入，以及旧存档摘要兼容；新的真实模型质量需要第二轮试读评估。

第一轮授权的 8 个场景已用完，第二轮属于单独的受限试读。
